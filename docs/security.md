# Threat table

The harness's security properties, each with the tests that prove it
(statewalker/statewalker-root#85). A row names its tests as `` `<package>`: "<test title>" ``,
separated by `;`. `ai-conformance`'s threat-table test fails CI when a row names no test or a test
that does not exist. Every ticket that touches a security property adds or extends its row.

| Property | Tests |
|---|---|
| Only access tokens the deployment's issuer signed, for this workspace and not expired, open a user session or reach the session API | `ai-conformance`: "refuses a request whose access token the issuer did not sign"; `ai-conformance`: "refuses an expired access token"; `ai-conformance`: "refuses to start an agent session without a valid access token" |
| Membership: a user holding no role in a project, in the role source that answers for it (the workspace's SQL or the project's access file, chained), cannot start an agent session there; a workspace admin is no member by being admin | `ai-conformance`: "refuses to start an agent session for a user not in the project's access file"; `ai-conformance`: "answers members and custom roles from the workspace's SQL"; `ai-conformance`: "answers a project from the first role source in the chain that knows it"; `ai-conformance`: "a workspace admin is no member of a project and cannot open a session in it"; `ai-access`: "a chain answers each project from the first source that knows it"; `ai-access`: "a member is a user holding at least one role that resolves" |
| Roles grant only what their permissions name, with targets relative to the project; Datalog in a role only narrows (only checks are accepted); an unknown area, action or role, a redefined built-in role and a cycle of roles grant nothing; the translation of permissions to Datalog decides as the plain matcher does | `ai-conformance`: "narrows a session to a custom role's targets, relative to the project"; `ai-conformance`: "lets Datalog in a role only narrow: a check narrows, a fact or rule grants nothing"; `ai-conformance`: "ignores unknown permissions and grants nothing through a cycle of roles"; `ai-access`: "decides exactly as the plain matcher does, for every kind of target"; `ai-access`: "never grants through an unknown area or action, whatever else the role holds"; `ai-access`: "adding a check to a role never widens it"; `ai-access`: "accept only checks as Datalog: a fact, rule or policy in a role is reported and ignored"; `ai-access`: "refuses Datalog comments, so joined checks never hide a policy or another check"; `ai-access`: "report a cycle and grant nothing through the roles in it"; `ai-access`: "report an unknown role and a custom role that would redefine a built-in one"; `ai-access`: "authorizes each file action by the permissions the member's roles grant at that moment" |
| No built-in role holds the network (`net.*`) or remote agents (`agents.use`), and `*` never reaches them; the workspace admin reads no project's files | `ai-access`: "give no built-in role the network or remote agents"; `ai-access`: "expands * over the known areas and actions, never to the permissions only named ones grant"; `ai-access`: "let the workspace admin manage projects and members but not read files" |
| Roles are read at every action: a demotion or removal reaches a running agent session at its next call, which is refused; its tool set is not rebuilt | `ai-conformance`: "a demotion in the access file reaches a running session at its next action, without rebuilding its tool set"; `ai-conformance`: "a demotion or removal in the workspace's SQL reaches a running session at its next action" |
| The workspace root key and every capability (user and agent session) stay on the server | `ai-conformance`: "lists the caller's agent sessions in the token's workspace, from the session index"; `ai-conformance`: "starts an agent session in a project the user is a member of" |
| An agent reads only inside its session's project, under every path form (absolute, relative, `..`, a sibling sharing the name's prefix), whatever its user's roles elsewhere | `ai-conformance`: "refuses the read tool a file outside the session's project" |
| The project's system folder is not there for an agent (ENOENT under every path form) | `ai-conformance`: "never lets the read tool see the project's system folder" |
| A user reaches only their own agent sessions | `ai-conformance`: "refuses a message to another user's agent session"; `ai-conformance`: "refuses to list another user's agent session" |
| Tenancy: a Workspace DO never calls a User DO; the gate takes user, project and session from the capability alone and answers while the User DO is unreachable | `ai-conformance`: "the gate answers an agent session's file calls while its User DO is unreachable"; `ai-conformance`: "a Workspace DO holds no way to call a User DO or the profiles" |
| One user's User DO never reaches another user's profile or sessions; a user name cannot place a profile outside `profiles/<user>/` | `ai-conformance`: "serves each user only their own folder of the profiles file system"; `ai-conformance`: "refuses a user whose name would reach outside their own profile folder"; `ai-conformance`: "refuses to list another user's agent session"; `ai-environment`: "never reaches another user's profile, under any path form"; `ai-environment`: "refuses a user name that is not one path segment"; `ai-access`: "mints no capability for a user name that is not one path segment" |
| A session is reached only with a token for its own workspace, and a token for a workspace the deployment does not serve is refused | `ai-conformance`: "lists another workspace's sessions only with a token for that workspace"; `ai-conformance`: "refuses a token for a workspace the deployment does not serve" |
| Attenuation only narrows: an agent session's capability cannot be moved to another project or session by a later block, and a bare user capability or another workspace's never passes the gate | `ai-access`: "an agent session's capability cannot be widened to another project by a later block"; `ai-access`: "refuses at the gate a bare user capability and one another workspace signed" |
| Erasing a user erases their profile and their User DO's storage, and no other user's | `ai-conformance`: "erasing a user erases their profile and their User DO's storage" |
| Modes and permission rules decide every action at that moment, after the roles: a mode switch reaches a running agent session at its next call; deny beats ask and ask beats allow across the deployment's, project's, user's, session's and mode's rules; `dontAsk` denies what no allow rule allows, `bypassPermissions` never asks but a deny rule still denies, `plan` writes only in its folders, `auto` is `default` | `ai-conformance`: "a mode switch reaches a running session at its next action"; `ai-conformance`: "decides by the rules of the deployment, the project, the user and the mode: deny beats ask, ask beats allow"; `ai-access`: "deny beats ask and ask beats allow, whichever layer holds each"; `ai-access`: "dontAsk never prompts: allow rules run, everything else is denied"; `ai-access`: "bypassPermissions never asks, and a deny rule still denies"; `ai-access`: "plan writes only in its configured folders and asks to widen or switch elsewhere"; `ai-access`: "treats auto as default until the risk classifier"; `ai-access`: "ignores an unknown mode name and malformed rules instead of widening" |
| Only the user switches modes and answers approvals: the gate takes a mode, the user's rules and a granted approval only with a bare user capability (an agent session's is refused), a mode switch needs the user's own access token, and an approval is reached only by its own user | `ai-access`: "takes the user session's own decisions (mode, rules, approvals) only from a bare user capability"; `ai-conformance`: "only the user switches modes, to a mode that exists, for their own sessions"; `ai-conformance`: "an approval is answered only by its own user" |
| "Ask" runs nothing until the user answers: the turn ends at the pending call, and approving runs exactly the stored action (keyed by session, method, path and content), once, re-checked against the current mode and the user's current roles; a denial writes nothing; an approval for the session covers only the same permission on the same target in that session | `ai-conformance`: "ends the turn waiting on an approval when the mode asks, listed on /v1/me and /v1/approvals"; `ai-conformance`: "approving runs exactly the stored action, once"; `ai-conformance`: "denying returns the user's message to the model and writes nothing"; `ai-conformance`: "a repeated identical action waits on the same approval"; `ai-conformance`: "approving re-checks the stored action against the current mode"; `ai-conformance`: "approving re-checks the stored action against the user's current role"; `ai-conformance`: "approving for the session lets the same action on the same target run for the rest of it"; `ai-access`: "an approval for the session covers only its own target, never a pattern a file name spells" |
| A pending approval expires (24 hours by default) and then counts as denied: it cannot be answered and its action never runs | `ai-conformance`: "approvals expire after their time and then count as denied"; `ai-conformance`: "ends the turn waiting on an approval when the mode asks, listed on /v1/me and /v1/approvals" |
| Writes, folders and deletes by an agent are authorized by its roles (`files.write`, `files.delete`) inside its project, never on a project's own folder; `mkdir -p` of an existing folder changes nothing and never asks | `ai-access`: "authorizes writes and deletes by the roles, like reads"; `ai-conformance`: "approving re-checks the stored action against the user's current role"; `ai-conformance`: "never lets an agent remove its project's folder, even where the mode never asks"; `ai-conformance`: "mkdir -p of an existing folder does not ask" |
| Secrets go only where their binding allows: a `{{secret:NAME}}` resolves only when the winning secret's binding names both the calling plugin and the request's host, so a project plugin cannot send a shared secret to an unbound host; a placeholder in the model's input, a body or the host never resolves | `ai-conformance`: "a project plugin cannot send a shared secret to an unbound host or use one not bound to it"; `ai-conformance`: "a deployment secret reaches only its bound plugin and host" |
| No API returns a secret's value: only names, levels, bindings and update times are listed, and only at a level the caller holds `secrets.write` for | `ai-conformance`: "lists a secret's name, level, bindings and update time, never its value"; `ai-conformance`: "manages secrets only at a level the caller holds secrets.write for"; `ai-access`: "grant secrets.write only by name: the owner a project's, the admin the workspace's" |
| Secret values never appear in items, the model's context, logs or error text: the gateway redacts them from what services answer, and items record only the names used | `ai-conformance`: "never shows a secret's value in items or error text, even when a service echoes it"; `ai-conformance`: "injects a bound secret into a tool's outgoing request, and the item names it" |
| Secrets below deployment level are sealed in the Workspace DO's SQLite under a key derived from `SECRETS_KEY` and the workspace, never in files; a sealed value opens only in its own row and workspace | `ai-environment`: "keeps values sealed under SECRETS_KEY, never in the clear"; `ai-environment`: "a sealed value moved to another row does not open" |
| Erasing a user erases their own secrets | `ai-conformance`: "erasing a user erases their own secrets" |
